# Repository Internal 

## What is an AT Repository ?

**a cryptographically authenticated, content-addressable data structure used to store and transfer public user data records**

## Why does every account have a repository?

**Every account has its own repository because the AT Protocol is designed to give you absolute control and ownership over your data, decoupling it from any single platform or server.**

## Repository Commits

A repository commit is a formal, published update to an account's data. Just like in software development (Git), every time you create a post, delete a comment, or follow someone, a new commit is generated. Instead of sending raw text, your Personal Data Server (PDS) bundles the change into a structured block of data that reflects the new, exact state of your account.


## Signed Commits

A signed commit is a commit that includes a valid cryptographic signature (sig) generated by your account's private key. Because every commit is signed, the data becomes self-certifying. Any server or user on the internet can verify the signature against your public Decentralized Identifier (DID). This proves that the post or action came genuinely from you, and that no intermediary server tampered with it.

## Repository Roots

The repository root is the single cryptographic hash (specifically a Content Identifier, or CID) that represents the top of your entire data tree (the Merkle Search Tree). You can think of it as a digital fingerprint of your entire account at a specific microsecond. If you change a single letter in an old post, the root hash changes entirely. A repository commit always points directly to this root.

## Content-Addressed
Data Content-addressed data means that data is found, retrieved, and verified based on what it is, rather than where it is stored. In the AT Protocol, every piece of data (a post, an image, a profile) is hashed to create a unique CID (Content Identifier). If a server wants to fetch your profile picture, it asks for the specific hash of that picture. It doesn't matter which server hosts it; if the hash matches, the data is guaranteed to be correct and unaltered.

## What is a DAG-CBOR ?

CBOR = Concise Binary Object Representation. It is a format that encodes JSON-like data in a binary form.


JSON: 

```
{
  "name": "Dayanch",
  "age": 29
}
```
CBOR:
```
JSON-like object
       ↓
     CBOR
       ↓
binary bytes
```
**DAG-CBOR, on the other hand, is a more restricted or canonical form of CBOR used by IPLD for DAG structures.**


**One of its key features is the ability to store CIDs directly as links.**


Example: 
```
Post
├── text: "Hello"
└── author: CID → bafy...
                    │
                    ▼
                  User
```
**This leads us to the DAG.**


## What is IPLD?

IPLD = InterPlanetary Linked Data

In the IPLD approach, objects can be linked to each other via CIDs:

````
Post CID: A
{
    text: "Hello",
    author: CID(B)
}

             │
             ▼

User CID: B
{
    name: "Dayanch"
}
````
